On the workflow itself — a few suggestions before the diagram:

The two-phase clustering idea is smart. One refinement: in the ingestion phase, consider using a lightweight deduplication step (MinHash or cosine similarity threshold) before clustering, so your clustering algorithm isn't fighting near-duplicate articles. Also, for the personalization clustering, rather than just thumbs up/down, consider implicit signals too — time spent reading, scroll depth, click-through. These are stronger signals than explicit ratings, which users often don't give.

One gap: you haven't mentioned a user profile store separate from the vector DB. The vector DB holds article embeddings; you'll separately need to store each user's cluster weight vector, which evolves over time. These are different concerns and should live in different stores.

For the "always-on" pipeline, consider thinking of it as two loops: a fast loop (every 15–30 min: fetch → deduplicate → embed → upsert into vector DB) and a slow loop (every few hours: re-cluster, refresh summaries, recompute trending weights). Running full clustering on every cycle is expensive.

1. Assessment of the workflow

Strong choices: two-phase clustering is genuinely clever, the implicit personalization avoids cold-start UX friction, and a RAG layer is the right call (better than fine-tuning for this use case). The suggestions I'd add:

Add a deduplication step before clustering (MinHash LSH works well). Otherwise near-identical articles waste cluster slots.

Separate fast and slow pipeline loops. Don't run full re-clustering every 15 minutes — it's expensive. Run a fast loop (fetch → deduplicate → embed → upsert, every 15–30 min) and a slow loop (re-cluster, regenerate summaries, recompute category weights, every 3–6 hours).

User profile store is its own component. Your vector DB stores article embeddings; you need a separate lightweight store (Postgres or Redis) for each user's cluster weight vector. These are updated in real time on every feedback signal.

Implicit signals over explicit ones. Thumbs up/down is good; combine it with dwell time (how long they read) and click-through rate. These are much denser signals.

2. Phased build plan

Phase 1 — Ingestion & Storage foundation (weeks 1–2)
Build the raw data pipeline: collect from NewsAPI/GNews + one scraper target, clean and normalize text (remove HTML, extract title/body/source/timestamp), store raw articles in a SQLite or Postgres database. Set up a simple scheduler (APScheduler) to re-run every 30 minutes. Goal: reliable flow of clean articles into a local store.

Phase 2 — Clustering & Summarization (weeks 3–4)
Generate sentence embeddings (all-MiniLM-L6-v2 from sentence-transformers is a great starting point). Run HDBSCAN or K-Means on those embeddings to form topic clusters. For each cluster, prompt an LLM (Ollama + Phi-3 Mini, which you already use in Smart Docs) to generate a 3–4 sentence summary. Store cluster ID, summary, and embeddings. This is the most technically interesting phase.

Phase 3 — Vector DB + RAG pipeline (week 5)
Upsert cluster summaries as vectors into ChromaDB (you have prior experience here). Build a basic LangChain RAG chain that retrieves top-k relevant clusters for a query and synthesizes a response. Test with simple keyword queries before adding personalization.

Phase 4 — Personalization layer (weeks 6–7)
Create a user profile schema: a weight vector over cluster categories (sports: 0.2, tech: 0.8, politics: 0.1, etc.). Initialize uniformly. Implement the feedback endpoint: thumbs up → +0.1 on that cluster's weight; thumbs down → -0.1, clamped and normalized. Modify RAG retrieval to bias toward clusters with higher user weights. Add dwell time tracking on the frontend.

Phase 5 — Frontend + full integration (week 8)
Build a FastAPI backend exposing /feed, /feedback, and /refresh endpoints. Build a minimal React or Streamlit UI showing the personalized feed with thumbs buttons. Wire the scheduler to the full pipeline. Do end-to-end testing.

Phase 6 — Hardening & polish (ongoing)
Add logging and monitoring (track cluster drift, user preference evolution), handle edge cases (new user cold start → show top trending clusters), and optimize embedding + clustering latency.

Key design decisions worth knowing

UMAP before HDBSCAN — MiniLM produces 384-dim vectors. HDBSCAN struggles with high-dimensional spaces (curse of dimensionality). UMAP collapses to 15 dims while preserving neighborhood structure, giving HDBSCAN much cleaner density signals.

Singletons don't call Ollama — articles HDBSCAN labels as noise get their title used directly as the label and body as the summary. Saves LLM calls and latency.

Summary embedding stored in the DB — each cluster's summary is itself embedded and stored as a BLOB. This is the handoff to Phase 3: the vector DB in Phase 3 will be seeded from these, not from raw article embeddings.

Incremental processing — the slow loop only processes new (is_processed=0) articles each run. Full re-clustering of history will be a separate command added in Phase 3+.
